# 消息、上下文与投递边界

QQ 消息先归一化、存储并判断回复网关，再下载当前图片、语音、视频及引用附件。平台消息按机器人账号、会话范围和平台消息 ID 去重；重复投递在网关和媒体下载前结束。数据库独立 `message_id` 用于关联附件、派生转发消息和引用定稿，时间字段仅表示时间。

上传文件保存在 `files/<time>-m<message_id>/`。文件名通过独占创建提前占位，避免同一消息被并发恢复时互相覆盖；取消时等待已启动的文件写线程结束后再清理未索引文件。

## 当前请求与历史

QQ 适配器将当前消息和历史分别交给中性 Core，后者保留历史信封并把当前媒体转换为模型内容块。前面的历史和引用属于背景，不能自动变成其他待回答的问题；当前请求明确要求汇总或同时回答时例外。承接表达仍可结合相关前文理解。

历史是触发消息到达时的快照，查询使用 `before_time` 排除当前消息。排队后不重新读取整个群的最新历史，避免把后到成员的问题加入本轮输入。排队期间新产生的助手回复也不会补入这个快照：用户发送本轮请求时尚未看到那些回复。需要新上下文时，由后续消息明确发起请求。

启用 `[sessions]` 后，执行前在机器人、会话、`id < 当前消息 ID` 和 `time < 到达时间` 的共同边界内读取冷启动或增量历史；热状态若已包含边界之后的输入／已投递回复，先使该代失效再重建。增量游标记录上次当前输入的 ID，已投递 assistant ID 单独去重，避免漏掉生成期间到达的群消息。配置和缓存容量降级仍遵守这些查询边界。

主 Agent 和文档子代理的 `MediaInputMiddleware` 在每次模型调用前、FilesystemMiddleware 恢复二进制内容后执行能力检查、图片规范化和预算限制。所有直接内联媒体共用 `max_inline_images` 和 `max_inline_media_bytes` 预算；由新的消息向旧消息分配，优先最近显式读取的附件、当前输入，再到旧历史，同条消息内保留原顺序。`read_file` 返回的图片和 PDF 也计入预算；大小未知的远程 URL 不绕过预算。省略媒体只保留说明与已有附件路径，不修改持久化消息，不在模型输入边界额外下载。

## 历史图片和文件

历史信封中的 `attachment_refs`、本地历史查询和平台历史查询中的附件列表提供原消息段的零基 `segment_index`。列表不含临时下载链接，也不会触发下载。原始消息即使未通过回复网关，仍可按这些编号恢复附件。

Agent 先用 `get_recent_conversation` 或 `search_messages` 确定消息和发送者；平台历史可用 `get_history_messages` 查询。随后调用 `get_message(message_scene="group", message_seq=..., include_attachments=true)` 获取当前群中该消息的附件路径，再调用 `read_file` 读取内容。`attachment_index` 可指定单个原始段编号；省略时每次最多暂存 4 项。其他项仍返回可继续读取的编号，不因前面下载失败而重新编号。

附件读取限制在运行时当前会话，支持同群不同发送者。私聊历史里附带的用户本人群发言不提供跨群附件引用；工具也拒绝跨会话加载。不明确指哪条消息时由 Agent 澄清，不自动选择全群最新附件。

读取复用已有消息、附件表和 TTL 缓存，不新增数据库表。缓存缺失或失效时复用引用消息的 Milky 下载与链接刷新逻辑；单项缓存用 `metadata_json.segment_index` 绑定原始段。旧缓存只有在编号映射明确时才复用。图片在暂存时校验，并将 BMP/TIFF 等转换成 `read_file` 支持的格式。文件成功暂存返回 `ready`，不代表模型已经读取或理解；资源失效、读取失败或模型不支持时保留明确说明。合并转发内的嵌套附件不在本轮单项编号范围内，仍沿用原引用/转发处理。

## 会话队列与期限

- `delivery:{workspace_key}` 覆盖 QQ 的模型生成、工件发送、最终回复发送及送达历史写入。同群不同成员共享队列；私聊按对端用户隔离。队列按进入锁等待的顺序执行，不保证不同事件预处理完成的顺序等于平台接收顺序。
- `workspace:{workspace_key}` 位于统一 Agent 执行边界，保护 QQ、定时任务等对同一 workspace 的并发执行。固定顺序是先取得 delivery 锁，再取得 workspace 锁；运行层和工具不得反过来获取 delivery 锁。
- `agent_job_timeout_seconds` 限制 QQ 的排队等待和后续处理总时长，包含生成及投递。运行层另有相同配置的执行期限，外层期限先到时取消正在执行的协程。网关前后媒体预处理仍使用各服务自己的超时。
- 排队超时的请求不会启动模型或工具；处理超时会传播取消并释放锁。超时提示绑定原消息，并有独立的 15 秒发送期限。新消息到达不会自动取消、合并或覆盖已有请求。

当前锁只协调同一进程。多进程部署需要额外的外部协调机制。已发生的平台工具写操作不会因模型失败或超时而回滚，也不会由消息入口自动重跑；持久化去重意味着进程中断后重复平台事件同样不会自动重新执行。

## 投递结果

`get_paint` / `get_video` 成功返回的工件在本轮 Agent 完成后统一投递，模型无需再调用媒体发送工具。`send_image` / `send_audio` / `send_voice` / `send_video` 只构建待投递工件，接受当前 workspace 与 `/memory/{workspace_key}/` 挂载中的虚拟路径，或 HTTP(S) URL；不会在工具执行时调用 Milky。路径越界、文件不存在、无效 URL 等发送前校验失败会返回错误说明和空工件，本轮可继续使用先前生成的工件，不会因此中止或重新生成媒体。工具内部的未知异常及真实平台写操作失败仍遵守原有中止规则，不自动重试。

`send_artifacts()` 只接收可发送的 `UniMessage`，结构化 MCP 字典不会进入发送路径。多媒体工件拆分后保留所有文本说明和原有顺序，串行发送，遇到失败停止剩余工件。

`send_messages()` 和 `send_artifacts()` 返回 `DeliveryResult(attempted, sent, errors, message_ids)`；最终回复的 `message_ids` 从 Milky 发送回执提取。文本失败可回退为图片；错误提示本身送达不代表原内容送达。QQ 的最终文本回执是 assistant 历史的提交边界：文本送达但前置附件失败时保留附件错误诊断并记录已收到的文本，文本失败时即使附件已送达也不写入文本历史；不会为这些情况重新执行 Agent。数据库写入失败不会重发已送达的内容；ACP 命令同样检查投递结果，并报告发送失败。

最终文本或 Markdown 渲染图的历史记录保存发送回执中的平台消息 ID，以及经过输出安全检查的原始文本。引用这类本地 assistant 记录时直接使用原文，不回源下载渲染图片；普通图片和回源引用仍由现有模型输入转换层校验、转换图片格式。旧记录若缺少发送回执 ID，无法可靠匹配到原文，保留平台回源行为。

`asyncio.CancelledError` 始终向上传播，不被当作普通失败吞掉。

QQ 会话租约覆盖生成、审核和投递。`awaiting_delivery` 不能被 TTL 或 LRU 删除；结算时在 workspace 锁内用实际送达文本替换最终 AI 消息。未完成投递和异常路径使代次失效，禁止恢复旧图中的待执行操作。清扫器仅在事件循环上同步删除空闲／失效代次，不跨 await 持有全局管理锁。媒体轮次结算后释放整代，旧工件不会重新发送。详见 [QQ 会话缓存](agent-sessions.md)。
